## 一、先准备什么，再开始编码

推荐顺序为：开发设计初稿 → 同步完善关键页面 UI 和前端方案 → 核对数据、接口与页面是否一致 → 按模块编码和联调 → 整体验收。

这里的“同步”是指两项设计可以交替完善，不需要先画完所有页面才能考虑数据库，也不能等后端全部完成后才发现页面需要的数据没有接口提供。

| 顺序 | 产出 | 需要解决的问题 | 完成到什么程度 |
| --- | --- | --- | --- |
| 1 | 开发设计文档 | 数据存在哪、如何关联，接口如何分工，消息和 AI 结果如何流转 | 主链路、关键表、接口约定、状态及异常处理可以对应起来，明确复用与改动范围 |
| 2，与第 1 项交替完善 | UI 设计与前端方案 | 线框最终长什么样，按钮和弹窗怎样操作，不同状态怎样呈现 | 统一视觉规则，完成关键页面及交互状态，列出可复用组件和页面取数关系 |
| 3 | 更新本清单的任务对应关系 | 每项开发改哪些模块，依赖什么，怎样验证 | 设计中的表、接口、页面和现有验收项能对应，不需要再复制一整套需求文档 |
| 4 | 实际编码与联调 | 把已设计的链路实现出来 | 每轮交付可操作的完整功能，并按对应验收项检查 |

**开发设计初稿已输出。** 先核对整体数据关系、表结构和主链路，再补足关键接口细节，并同步推进 UI；本清单不代替设计文档。

## 二、开发设计文档要包含什么

建议先集中在一份文档中，便于来回核对。接口参数过多时再独立整理接口文档，不提前拆成大量文件。

### 2.1 现有工程与改动边界

- 以 AgentServe 的 FastAPI、SQLAlchemy、Vue、Pinia 和 Element Plus 为基础，优先复用已有服务、页面及组件。
- 列清本次新增、扩展和继续沿用的部分；HelpPilot 只按明确需要选择性参考，不进行整套工程合并。
- 说明运行依赖、配置、数据库及向量检索方式，区分原工程已经具备的条件与本项目仍需补齐的条件。

### 2.2 数据模型与数据库表设计

先给出“店铺—客服—客户—聊天—人工接待事件—订单—工单—知识—调用记录”的关系，再展开表结构。

每张涉及改动的表说明：用途、原有或新增、字段及类型、是否必填、默认值、关联关系、唯一约束、查询索引，以及旧数据如何迁移。这里的 models 指业务数据模型，不意味着要新增一张名为 models 的模型目录表。

| 数据范围 | 设计时需要说清楚 |
| --- | --- |
| 店铺与账号 | 一个租户一个平台一家店；客服与客户如何归属店铺，登录怎样识别归属；同店共享与跨店隔离如何落到查询和关联校验 |
| 客服接待端 | 手动在线、账号启停、实际连接、有效登录端分别如何记录；新端登录如何让旧端失效 |
| 聊天与人工接待事件 | 客户聊天入口连续保留，但可以完结、重新咨询、新建人工接待事件；这些概念如何在数据上区分，历史记录如何关联 |
| 商品、规格及客户资料 | 公共商品与规格分别建模，保留原规格 ID、订单成交快照及库存归属；批量创建原子提交；客户备注手动维护，不向店铺开放人工新增客户 |
| 文件与头像 | 商品图片 5 MB、客服头像 2 MB，均限 JPG／PNG／WebP；文件归属与业务资料绑定，不能挤进必须关联聊天的消息附件结构 |
| 会话摘要 | 结束后异步生成一句话，只读取该次接待；明确状态、去重、失败恢复及用量分类，不把首条消息当作摘要 |
| 消息与 AI 建议 | 客户已收到的消息、内部未发送建议、生成任务如何区分，怎样对应提问、接待人及 Token 用量 |
| 订单关联与客服工单 | 一张工单固定关联一家店、一个客户、一笔订单和一次会话；同次诉求补充如何合并，后续新事件如何另建；完成标记与完成客服、时间如何保存 |
| 知识与版本 | 分类、文档、切片、用途说明、每篇分段参数、有效时间和上一已发布版本如何关联；向量怎样绑定店铺、知识版本及向量化模型，切换模型或维度时怎样重建，避免混用旧向量；优先扩展现有结构 |
| 店铺配置 | 三类模型配置与密钥、整店接待开关、欢迎语和检索设置怎样复用现有配置能力，密钥怎样安全保存 |
| 追踪与统计 | 人工求助、实际接入、AI 调用、业务写操作及评价如何关联；是否已有足够记录计算本版指标 |

表的数量和字段不在实施清单中提前定死。能由现有结构可靠表达的就复用，需要独立生命周期或约束的再新增。尤其不能把现有待确认业务动作 PendingAction 直接当成客服工单。

同时明确数据库升级与失败恢复方案。现有 SQLite 启动建表行为不能代替对已有表的字段迁移。

### 2.3 路由与接口设计

本项目有三种容易混淆的“路由”，设计中分别写清：

| 名称 | 负责什么 | 要写出的内容 |
| --- | --- | --- |
| 后端 API 路由 | 页面向后端读取资料、提交修改或执行已有业务 | 请求方式、路径、参数、返回、分页、归属校验、错误情况，以及重复提交如何处理；标出沿用、修改或新增 |
| 前端页面路由 | 菜单进入哪个页面，详情与返回怎样保留位置 | 五个模块的页面入口、列表到详情的关系、页签和筛选状态、从会话跳转路由记录后的返回方式；是否沿用现有页面切换方式在此确定 |
| AI 处理路由 | 本轮应查业务、查知识、追问、回答或求助人工 | 模型判断的输入输出、固定程序校验、允许操作、异常兜底；与知识分类筛选、切片检索分别表达 |

接口还需区分：普通请求、回复生成过程、消息及列表更新通知。对实时更新采用什么方式、连接失效如何恢复、旧登录端如何停止操作，在这里一并确定，避免每页各做一套。

### 2.4 数据流、状态与异常处理

至少把以下链路按“输入 → 校验 → 查询或模型调用 → 保存 → 页面更新”写清，并列出失败后保留什么、用户看到什么：

1. 客户发消息：识别店铺及当前接待状态，保存消息，选择 AI 或人工路线，检索或查业务，保存回答和追踪，更新聊天。
2. 知识发布：上传解析、生成用途、设置分段并预览、向量化、发布与有效时间过滤；失败保留原可用内容，恢复上一版保留原日期。
3. 人工求助与接入：创建或复用等待事件，共享展示；并发接入只有一名成功，取消该事件已经不适用的延迟安抚。
4. 人工回复辅助：生成内部建议、关闭、失败和发送；用会话及生成任务标识识别过期结果，避免覆盖手动输入或发给客户。
5. 工单记录：AI 或客服整理诉求，校验客户、订单、会话归属，重复补充合并；手动完成只更新工单记录。
6. 完结与重开：区分客户聊天入口、当前接待阶段和人工事件，明确新建人工事件与原记录保留的数据变化。
7. 时间与连接：5 分钟 AI 完结、300 秒一次安抚、30 秒断线补位；说明计时起点、取消条件、并发和服务重启后的补偿方式。
8. 召回测试：使用正式有效知识，但隔离客户消息发送、工单创建、人工求助和业务写入；测试结果不计入客户会话用量。
9. 原有业务确认：保留取消订单、申请退款的客户确认和执行校验；和工单记录分开，结果待核实时不提示已完成。

模型超时、无效 Key、检索无结果、消息发送失败、多个客服同时操作等，在对应链路内说明，避免只写成功过程。

### 2.5 前端方案、迁移与验证

- 页面与组件：保留哪些，拆分哪些，每页需要哪些接口与更新通知；工作台按客户入口取数，历史与工单复用会话抽屉、回复路由在来源页弹窗查看。
- 状态归属：店铺共用数据、客服个人状态、单会话草稿与生成任务分别放在哪里，避免切换会话串内容。
- 迁移：旧账号角色、账号与店铺关系、旧知识和配置如何转换，顺序和恢复办法是什么。
- 验证：把关键设计对应到现有验收项，补充并发接入、跨店访问、旧端失效、迟到生成结果、定时重复执行等有实际风险的检查。

## 三、UI 和前端在编码前确认到什么程度

现有线框已经确认布局、入口和主要操作，现已确认灰白底＋靛蓝主题及关键交互，后续以当前前端和验收标准核对接口及状态，不重新开启配色确认。建议继续基于现有 Vue 与 Element Plus，不先更换整套技术或组件库。

| 设计范围 | 需要确认的内容 |
| --- | --- |
| 应用外框与通用规则 | 导航、页头、字号、间距、颜色、表格、表单、弹窗和状态标签；确认主工作区在目标桌面尺寸下可用 |
| 会话工作台 | 三栏比例、消息身份、AI／等待／人工阶段、相关订单及工单；AI 生成只读、关闭、失败、可编辑、发送中，以及已被其他客服接入的呈现 |
| 待办事项 | 两个页签、列表密度、两种新增入口、关联字段锁定、编辑和标记完成；沿用已确认流程，不增加新的业务审批 |
| 知识编辑与预览 | 分类、正文与用途说明的位置，左侧分段设置及右侧预览，预览失效提示、向量化和发布失败呈现 |
| 模型配置与平台设置 | 三类配置卡片、Key 遮挡、配置验证、整店 AI 启用入口；五个设置页签、固定规则和欢迎语 |
| 分析、历史及电商页面 | 统一列表和详情样式；数据卡片、趋势与口径说明；优先适配原有页面，不重新发明业务操作 |

每个关键页面补齐正常、加载、无数据、失败、不可操作等适用状态，并核对按钮需要的接口和数据。复杂状态优先集中在工作台、知识发布和模型配置，不要求把每个普通列表都画成多份完整稿。

**不必等所有页面逐像素画完再设计后端。** 数据关系、状态和接口约定稳定后，可准备对应开发；前端实际编码前应完成该模块的关键 UI。五个模块已经按后续确认进入本地交互前端实施，后端按详细设计继续推进，不因此提前执行数据库迁移。

## 四、按模块整理实施任务

下列任务均为计划项。模块顺序用于阅读，实际开发按下一节依赖顺序安排。

| 模块 | 复用基础 | 主要实施任务 | 交付检查 |
| --- | --- | --- | --- |
| 通用基础 | 已有租户字段、认证、账号与配置 | 去除固定店铺限制，落实一个店铺的共享范围；统一店铺客服角色；有效接待端、手动在线及停用校验；配置与密钥隔离；数据库迁移 | 两店互不访问，同店多人共享正确；旧端及停用账号不能继续接待 |
| 客服中心／会话工作台 | 会话、消息、唯一接入、完结 | 三栏布局、共享等待且 AI 继续回应、三条时间规则、重开与人工事件关系、内部回复建议、会话独立草稿、图片及卡片 | 同一客户聊天连续，接入唯一，建议不自动发送，迟到结果不覆盖人工内容 |
| 客服中心／待办事项 | 可复用订单查询、列表和表单 | 新增订单诉求工单、AI 整理及校验、两个手动入口、同事件补充合并、两个完成页签及完成记录 | 同店可见，关联正确，不重复建单；完成标记不改变电商数据 |
| 客服中心／历史会话记录 | 会话、消息与路由追踪 | 全店已完结记录、AI 一句话摘要及失败状态、共用会话抽屉、单条提问路由弹窗、会话 Token 汇总 | 历史与路由正确对应，未发送辅助计入，独立测试、知识导入及摘要调用排除；摘要用量单独留存且不影响接待用量完整性，用量未知显示“—” |
| 电商管理 | 客户、商品、订单、支付、物流、退款与库存 | 商品公共信息及多规格、图片、整体创建事务、首规格售价；保留原规格库存及订单服务；客户移除人工新增并补手动备注，适配店铺与统一客服角色 | 原有业务结果一致；工单七种诉求不扩展为七套业务执行流程 |
| AI 与知识／模型和编排 | 三类模型、规则与语义分类、工具及确认流程 | 店铺模型和 Key 配置、验证及启用；固定基础规则与可编辑业务 Prompt 分离；增强语义判断；复用查询及允许写入检查；相关历史按需使用 | 配置按店铺取用，模型判断不跳过程序校验，异常仍可人工接续，无关问题正确引导 |
| AI 与知识／资料和测试 | 文档、版本、切片、向量化与检索 | 分类及用途说明、每篇分段预览、全店检索参数、逐步筛选、直接发布、上一版恢复、只读连续召回测试 | 仅已发布有效知识参与；过期及失败行为正确；测试没有正式接待和业务副作用 |
| 分析与反馈 | 追踪、反馈与原统计 | 四组追踪筛选及返回、单条赞踩、按最新状态待跟进、日期统计及口径 | AI 独立接待、实际写操作和人工工单完成分别计算，异常和无分母正确表达 |
| 平台设置 | 平台账号、客服账号与部分配置 | 五个页签、单店信息、头像及账号管理、固定规则、默认关闭的打招呼、必填 Score 及范围校验 | 同店配置一致，欢迎语按条件发送一次，固定时长只展示不自定义 |

## 五、后续编码顺序与阶段交付

先把能够贯通工作的主流程做完整，再补齐各模块。验收所需的追踪信息在发生业务时就记录，数据面板可以稍后展示。

| 阶段 | 主要工作与依赖 | 阶段交付 |
| --- | --- | --- |
| 0：设计准备 | 本清单、开发设计、关键 UI 与前端方案，核对三者一致 | 本清单、已合并最新需求的开发设计和五个模块的本地交互预览已就绪；目标后端、数据库及联调仍需实施 |
| 1：店铺与账号基础 | 数据迁移、认证范围、统一角色、共享与隔离、有效登录端；同步打通基础聊天持久化 | 已完成首批并通过 SQLite／MySQL 检查；真实工作台、客户聊天、账号与历史可用；旧归属回填另行核对 |
| 2：AI 接待基础 | 模型配置、密钥、基础 Prompt；知识分类、发布检索及测试；接待启用 | 已走通真实模型配置、Key 保护、知识发布／有效期、检索、自动回答、转人工和调用追踪；外部队列、OpenSearch、业务 Prompt 编辑及知识切片单独编辑后续完善 |
| 3：人工接续 | 事件与状态、共享等待、并发接入、消息更新、回复辅助、定时及断线处理 | 基础人工接入、回复、完结与再咨询已前置完成；AI 回复辅助、定时及断线补位仍待实现 |
| 4：工单及业务关联 | 工单模型、两个手动入口、AI 自动建单、待办完成；关联原电商资料和操作 | 一段会话多笔订单能分别记录，工单完成和原业务操作互不混淆 |
| 5：历史及分析 | 补齐历史查询、异步会话摘要、完整路由筛选及快照、Token、反馈与待跟进，按既定口径汇总 | 从历史追到具体提问和结果，数据能够核对到来源 |
