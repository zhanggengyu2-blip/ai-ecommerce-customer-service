# 第一版业务流程

本文件回答：客户、AI、客服和电商平台分别做什么，事情怎样得到解决。系统状态、按钮与异常响应见[功能流程](./第一版功能流程.md)，交付项目见[功能清单](./第一版功能清单.md)。

依据：[已确认产品定义](./第一版产品定义.md)。以下是对已定需求的流程整理，不增加业务审批、独立任务或新的角色；真实淘宝能力仍待联调验证。

## 1. 参与者与职责

| 参与者 | 负责的事情 |
| --- | --- |
| 客户 | 在淘宝原聊天框咨询、补充信息和图片，在淘宝 App 提交需要的售后申请 |
| AI 客服 | 理解诉求、查询信息、检索适用知识、追问和回答；需要人工时整理上下文；人工接入后提供内部回复草稿 |
| 店铺客服 | 接入需要人工的事项、核实和决定、与客户沟通；到淘宝后台办理必要审批，记录协商内容并手动完结会话 |
| 淘宝及实际履约方 | 提供订单、物流、售后和资金等实际状态；按适用规则办理申请、运输、退款或换货 |
| 产品方 | 内部开通店铺和初始账号、维护平台公共政策、处理暂不提供自助页面的维护事项 |

“商家”是店铺主体，不另设店铺端角色。同一店铺多个客服共用知识和配置，个人接待归属、输入草稿和在线状态各自独立。

## 2. 先区分三个概念

| 概念 | 例子与边界 |
| --- | --- |
| 客户聊天窗口 | 客户一直使用同一个淘宝聊天框，AI 与人工切换不跳页面 |
| 一次人工客服会话 | 一次需要人工解决的事件；同次事件可以有多个订单、部分商品和不同售后方式 |
| 售后业务进度 | 已申请、已审批、已寄回、已退款等实际进展，由可靠平台状态或真实处理结果确认 |

人工接入后，等待查证、物流或平台结果时可以继续保持会话在线，由客服判断何时回复及完结。**会话完结不等于售后办结；协商同意也不等于退款或发货完成。**

## BF-01：客户咨询与 AI 解决

**开始：** 客户在淘宝原聊天框提问；本地测试输入界面只用于开发验证。

1. AI 了解客户当前诉求；按需读取相关上下文，检索场景指引、平台政策、店铺政策和商品业务备注。
2. 涉及具体商品、订单、物流、库存或售后进度时，查询授权可得的实际信息；缺少必要信息就追问。图片可辅助核实，不确定的地方继续确认。
3. 对有依据的常规问题直接解释或指导操作。预计补货、规则描述与实际库存、退款结果分别表达，不提前承诺审批成功。
4. 问题已回答且不需人工，继续由 AI 接待；符合纯 AI 空闲结束规则时结束本次接待。规则详见 FF-05。
5. 无法可靠判断、需要店铺决定或客户明确要求人工，进入 BF-02。客户明确要求人工时不强制先走一轮 AI 问答。

**结果：** 客户得到有依据的答复，或带着已收集信息等待人工，无需重新叙述全部经过。

## BF-02：需要人工时的接续

1. AI 将当前诉求、相关订单、已核实事实及尚待决定的事项整理为一次人工客服会话。
2. 本店所有在线客服看到同一等待项；第一位成功接入的客服负责后续处理，其余客服不能同时接入。不轮询、不转接、不设接待名额。
3. 等待期间，AI 继续回答能确认的部分、补充必要信息；没有客服在线时仍保留等待。超过 300 秒无人接入，按知识库场景安抚一次，不取消等待。
4. 客服接入后查看本次完整聊天和主要诉求，接着核实与处理。客户仍在原聊天框，回复者名称变为客服。
5. AI 为客服生成内部草稿，客服可修改、清空、关闭辅助或点击发送。草稿未经人工发送，不成为客户收到的消息。
6. 客服完成当次沟通后手动完结；需要继续等待外部结果也可保持在线。客户主动结束且平台可可靠通知时，按实际结束处理。

**结果：** 同一事件由一名客服持续处理，留下接待经过、可靠结果和必要备注；不另建任务清单或独立方案审核。

## BF-03：售后业务处理

### 通用路径

**提出诉求 → 核对订单、商品、数量和问题 → 结合适用政策说明处理方式 → 客户在淘宝申请／补充材料 → 客服按需在淘宝后台办理 → 跟进实际结果。**

AI 可指导条件清楚的常规申请；发生争议、例外或需要店铺决定时，由客服接入。下列节点按实际业务适用，不要求每次售后都依次走完。

| 场景 | 要核对什么 | 实际办理与本产品的作用 |
| --- | --- | --- |
| 未收到货 | 订单、发货及物流状态、客户反馈 | AI 查询并解释；需核查异常或协商方案时交人工。物流异常不直接等同退款成功 |
| 退货退款 | 商品及数量、原因、可适用的退货约定、当前售后状态 | 客户在淘宝申请，客服在淘宝后台按需审批；是否需寄回、何时退款，以适用政策和平台实际状态为准 |
| 换货 | 原商品及数量、目标规格、库存及协商内容 | 引导淘宝换货申请，客服到淘宝后台办理；查询可得的寄回和补发信息，不能把预计安排表述为已发货 |
| 破损／质量问题 | 涉及商品、问题描述、必要图片、订单状态 | AI 收集材料和检索指引，需判断责任或例外处理时交人工，之后走双方确认的适用售后方式 |
| 错发／漏发 | 原订单、实际收到的商品和数量、必要图片 | 核实差异，由客服按适用政策与客户确认补发、退换或其他方案；以真实办理结果记录 |

退款不固定为“收到退货后才退”：有的平台政策或服务可能使退款更早发生。本文不预设具体时点，也不将政策文字当作资金已经到账的证据。

运费、补差价等少见协商按实际平台规则和客服处理结果记录，不新增支付、赔付或专门财务流程。本工作台第一版不直接执行淘宝退换货审批。

### 多订单、部分商品和混合方式

例：客户同一次咨询中提出，订单甲退一件，订单乙换一件。

1. 在同一次人工客服会话中核对两个订单，分别说明涉及的商品、数量和方案。
2. 客户按淘宝实际要求提交申请，客服在淘宝后台分别办理；外部可能有多个售后记录或物流记录。
3. 本产品仍保留一次人工客服事件，处理记录说明各订单的实际结果，不按订单、方式或外部申请数量拆出多个人工事件。
4. 当次事件结束后，客户后来提出另一件需要人工解决的事情，可以产生新的人工客服会话。

## BF-04：完结、再次咨询与原生人工接待

| 情况 | 业务上的接续方式 |
| --- | --- |
| 人工接待尚未完结，客户再次发消息 | 继续交当前客服 |
| 会话已完结，客户再次发消息 | 默认 AI 接待，按需读相关历史；需要人工再进入共享等待 |
| 客服从历史记录主动重新发起 | 选择继续原人工客服会话或创建新事件，客户聊天窗口保持连续 |
| 商家已在淘宝原生端回复／接管 | 在可靠识别接管的前提下暂停本系统 AI 对客回复与待接提示，避免双方同时接待；恢复需可靠交回信息或人工明确操作 |
| 当前人工实际失去服务连接 | 经短暂重连机会后由 AI 补位；客服回来后明确接回，不把手动离线等同失联 |

淘宝原生接管及客户主动结束的识别，均依赖平台实际事件能力，不以“暂时没消息”猜测。

## BF-05：店铺准备与知识维护

1. 产品方内部开通“一租户、一个平台、一家店铺”，提供初始账号。店铺客服共同管理本店客服账号。
2. 店铺完成淘宝授权，并配置自带 Key 的对话推理、向量化、重排序模型。真实权限、模型可用性须验证。
3. 店铺可通过少量选填问答建立本店售后规则，也可自由补充或导入 Markdown；不要求从空白文档写完整政策。具体问卷题目后续设计。
4. 店铺维护场景处理指引、商品业务备注和 Prompt。平台公共政策由产品方维护，店铺不能改写其他店铺资料。
5. 修改知识时可先用当前内容“试问 AI”，也可直接发布；商品业务备注提交即生效。试问不会发给真实客户或产生真实人工待接。
6. 知识可设生效／失效时间；不填长期有效，到期停止作为当前知识使用，保留记录、不自动恢复旧版。只提供上一版恢复，并保留原失效时间。

同店知识和配置共用；跨店数据与配置隔离。AI 可按需引用相关历史聊天，包括当时引用过、现已过期的知识内容，但这不会使原知识重新发布生效。

## 3. 与三条验收的对应

| 已确认验收 | 业务观察重点 |
| --- | --- |
| AI 实际解决常规咨询 | BF-01、BF-03：答复结合知识与实际查询，缺信息会追问，不能可靠处理会求助人工 |
| 人工接续完整可用 | BF-02、BF-04：多人看到同一等待项、唯一接入、人工决定发送、手动完结；多订单混合事项不重复建事件 |
| 真实接入与隔离通过验证 | BF-01、BF-05：真实淘宝消息及必要查询可用；同店共用、跨店隔离，模拟演示不能代替真实验收 |

后续页面、功能和实现设计以这份业务路径及产品定义为依据；平台能力冲突另记证据和影响，不静默改变范围。
